# 평가 방식

골든 데이터셋([DATASET.md](DATASET.md))으로 무엇을 어떻게 재고 어떻게 판정하는지 정리한다.
실행 순서와 합격 기준은 [PLAN.md](PLAN.md)에 있다.

## 1. 무엇을 실행하나

러너(`eval/runner`, `cargo run --release --example eval`)는 서버를 띄우지 않고
`jev_tree::engine::execute`를 직접 호출한다. `POST /api/run`이 부르는 것과 같은 함수이고,
HTTP 계층이 하는 요청 검증(`RunRequest::validate`)과 실행 제한 시간(기본 120초)도 똑같이 적용한다.
빠지는 것은 JSON 직렬화와 로그인 확인뿐이다.

한 번의 실행은 **셀(cell)** 단위로 나뉜다. 셀 = 라우터 설정 × 트리 변형이다.

| 축 | 값 | 뜻 |
|---|---|---|
| 라우터 | `jev` | Jev 빔이 카테고리를 고르고 Jev가 아이템을 랭킹 |
| | `jev_llm` | LLM이 카테고리를 고르고(루트 1회 + 서브트리 1회) Jev가 랭킹. LLM 호출이 실패하면 Jev 빔으로 대체 |
| 변형 | `deep` · `standard` · `shallow` · `flat` | 같은 아이템, 다른 트리 깊이 (7 · 4 · 2 · 1) |
| | `sparse` | standard 트리, 리프당 아이템 1개. 답이 빠진 질문은 보류가 정답(`dropped`) |

- search 케이스는 셀마다 시드된 DB 하나를 같이 쓴다(검색은 읽기만 한다).
- ingest 시나리오는 케이스마다 새 DB를 만든다. 저장 결과가 다른 케이스에 새지 않는다.
- 케이스는 기본 4개씩 병렬로 돈다(`--concurrency`). 지연 시간을 정확히 재려면 `--concurrency 1`.
- 모델 키는 결과 파일에 절대 쓰지 않는다. 모델 이름만 남긴다.

## 2. search 판정

### 2.1 라우팅

착지 노드(`leaf_id`)를 기대 노드와 비교한다. 허용 집합 = `expect.node` + 변형에 있는 `also_ok`.

| 유형 | 조건 |
|---|---|
| `exact` | 착지 노드가 허용 집합에 있음 (기대가 null이면 착지도 null) |
| `shallow` | 착지 노드가 기대 노드의 조상 (너무 일찍 멈춤) |
| `deep` | 착지 노드가 기대 노드의 자손 (막연한 질문인데 한 갈래를 찍음) |
| `branch` | 같은 영역의 다른 갈래 |
| `domain` | 다른 영역 |
| `false_none` | 트리 안 질문인데 null (답을 포기) |
| `false_tree` | 트리 밖(또는 가상 루트 밖) 질문인데 어딘가에 착지 |
| `error` | 실행 오류(Jev 장애, 제한 시간 초과 등) |

- **라우팅 정확도** = `exact` 비율.
- **계층 F1(hF1)**: 조상 집합 기준 precision/recall의 조화평균(Kiritchenko 방식). 형제 리프로 가면 부분 점수를 받는다.
  허용 집합이 여럿이면 가장 높은 값을 쓴다. 기대·착지 중 한쪽만 null이면 0.
- **깊이별 경로 일치율**: forest 진입 케이스에서 착지 경로의 상위 k단계가 정답 경로와 같은 비율.
  d1이 영역 선택 정확도다. 어느 깊이에서 무너지는지 본다.

### 2.2 답변

엔진 규칙대로 `abstained: true`(top 점수 < 0.30)이거나 `leaf_id: null`이거나 아이템이 없으면 "답하지 않음"이다.

| 지표 | 정의 |
|---|---|
| **E2E 정답률** (헤드라인) | answerable 케이스: 답했고 top1이 등급 2. 답할 수 없는 케이스: 답하지 않음 |
| 확신 정답률 | answerable에서 top1이 등급 2이고 role이 `recommended` |
| 오보류율 | answerable인데 답하지 않은 비율 |
| 오답변율 | 답할 수 없는(빈 리프·답 없음·트리 밖) 케이스에 답한 비율 |
| 트리 밖 판정 P/R/F1 | 양성 = `leaf_id: null`. 트리 밖·루트 밖 케이스를 얼마나 정확히 걸러내는지 |

### 2.3 랭킹

answerable 케이스만. 정답 = 등급 2 아이템. 반환 목록은 `limit`(기본 8)개까지다.

| 지표 | 정의 |
|---|---|
| Hit@1 · Hit@3 · Hit@k | 상위 1·3·k 안에 등급 2가 있음 |
| MRR@k | 첫 등급 2의 순위 역수 평균 |
| nDCG@k | 이득 2^등급−1 (등급 2 → 3, 등급 1 → 1), 이상적 순서 대비 |
| Recall@k | 등급 2 중 반환된 비율 |
| recommended 정밀도 | role이 recommended인 아이템 중 등급 1 이상 비율. 과잉 추천을 본다 |
| 라우팅이 맞았을 때 Hit@1·MRR | 라우팅이 exact인 케이스만. 랭킹 자체의 품질 |

라우팅이 틀리면 정답 아이템이 후보에 없으므로 랭킹 지표도 0이 된다.
그래서 "E2E 랭킹"(전체)과 "라우팅이 맞았을 때 랭킹"(조건부)을 같이 본다.

### 2.4 비용

| 지표 | 정의 |
|---|---|
| 지연 p50/p90/p95 | 케이스 한 건의 벽시계 시간. 병렬 실행 중 경합을 포함 |
| 라우팅 구간 | 시작 → descent 완료 |
| 랭킹 후보 수 | 착지한 서브트리의 활성 아이템 수 (`retrieval_completed.count`) |
| Jev 호출 수 | 빔 라운드 수 + ⌈후보 수 / 32⌉ |
| LLM 호출 수 | LLM 라우팅 호출 수 (재시도 제외) |
| LLM 대체율 | `jev_llm`인데 trace가 `beam`인 비율 (LLM 실패 → 빔) |

## 3. ingest 판정

시나리오마다 새 DB에서 다음을 차례로 한다.

1. **초안 저장**: `auto_publish: false`로 ingest.
2. **초안 확인**: 저장소에서 상태가 `draft`이고 활성 목록에 없는지 확인한다.
   `--verify-draft-search`를 켜면 probe 질의로 실제 검색해서 초안이 결과에 없는지도 본다.
3. **게시**: 받은 `item_id`와 `version`으로 `auto_publish: true`를 보낸다. (게시 요청도 descent를 다시 돈다.)
4. **probe 검색**: 케이스에 probe가 있으면 게시 후 그 질의로 검색해 새 아이템이 나오는지 본다.

| 지표 | 정의 |
|---|---|
| **저장 정확도** (헤드라인) | 저장 기대 케이스는 카테고리가 허용 집합에 있음, 거절 기대 케이스는 400이고 행이 늘지 않음 |
| 초안 비노출 | 초안이 `draft` 상태이고 활성·검색 결과에 없음. 100%가 아니면 불변식 위반 |
| 게시 성공 | `published_id = item_id`, 버전 +1 |
| 초안→게시 카테고리 유지 | 게시 때 다시 돈 descent가 초안과 같은 카테고리에 착지 |
| 중복 탐지 P/R | 기대 카테고리에 착지한 경우에만. 기대값은 엔진 규칙(3-gram ≥ 0.6)으로 검증된 라벨 |
| 갱신/신규 판정 | 같은 질문이면 기존 행 갱신(`updated`, 같은 id), 아니면 새 행 |
| 기존 답변 강등(관찰) | 이미 게시된 질문을 초안으로 다시 보내면 그 행이 `draft`로 바뀌어 검색에서 사라진다. 건수만 센다 |
| probe top-k 포함 / top1 | 저장한 지식을 나중에 찾을 수 있는지 |

## 4. contract 판정

모델 호출 전에 끝나는 요청 검증·경로 검사(404, 400)만 넣었다. 기대 오류 코드와 같으면 통과. 100%가 기준이다.

## 5. 집계와 통계

- 비율은 **Wilson 95% 구간**, 평균은 정규근사 95% 구간을 함께 적는다.
- 실행 오류(Jev 장애·시간 초과)는 품질 지표에서 **실패로 센다**(보수적). 오류 건수와 코드는 따로 보고한다.
- 반복 실행(`--repeat N`)이 있으면 같은 착지·같은 top1·같은 정오 판정 비율로 **안정성**을 낸다.
  이 값이 두 설정 간 차이를 해석할 때의 잡음 바닥이다.
- **임계값 스윕**: 기록된 top 점수로 보류 임계값 t를 바꿨을 때 E2E·답변 커버리지·답변 정밀도·오답변율을 다시 계산한다.
  현재 엔진 값은 0.30이다. 모델 호출 없이 보정 방향을 가늠한다.
- **짝 비교**(`compare`): 같은 케이스끼리 짝지어
  - 정오(E2E, 라우팅, Hit@1, 저장, 계약)는 **McNemar 정확검정**(불일치 쌍만 사용),
  - MRR 차이는 **짝 부트스트랩 95% 구간**(2,000회)으로 본다.
  - 나빠진 케이스와 좋아진 케이스 목록을 함께 낸다.
- 표본 크기 감각: 케이스 300건, 불일치 쌍이 15% 안팎이면 약 5%p 차이부터 유의하게 잡힌다.
  세부 분석 표(스타일·문맥 패턴별)는 칸마다 n이 작으므로 방향만 읽고 단정하지 않는다.

## 6. 세부 분석 축

리포트의 세부 분석 표는 E2E·라우팅·Hit@1·MRR·p50을 다음 축으로 나눠 보여 준다.

| 축 | 값 | 알고 싶은 것 |
|---|---|---|
| expect | leaf · internal · no_answer · empty_leaf · dropped · oos | 어떤 종류의 기대 결과에서 틀리나 |
| turns · ctx | single/multi, coref·ellipsis·refine·slot·shift·distract·correct·disambig·long | 문맥을 제대로 쓰나 |
| entry | forest · root · start | 가상 루트·시작 노드에서 동작 |
| level · depth | 목표가 리프/중간 노드, 목표 깊이 | 깊이가 늘면 무너지나 |
| pool | 0 · 1 · 2-5 · 6-32 · 33-100 · 101+ | 후보가 많으면 랭킹이 무너지나 |
| style | 15개 질의 스타일 | 어떤 표현에 약한가 |
| domain · diff · split | 영역, 난이도, dev/test | 편향과 과적합 |

## 7. mock 실행

`--mock oracle`은 스크립트 평가기가 라벨된 노드로 곧장 내려간다. 키가 필요 없고 비용이 0이다.
라우팅이 100%로 나와야 하고, 저장·거절·계약도 100%여야 한다. 아니면 라벨이나 하네스가 틀린 것이다.
랭킹은 상수 점수라 의미가 없다. `--mock abstain`은 항상 "해당 없음"을 고르는 기준선이다.
mock 결과는 품질 수치가 아니며 history에 남지 않는다.

## 8. 한계

- 결과는 `jev-latest` 별칭이 가리키는 모델 버전에 묶인다. 실행 기록의 날짜와 모델명을 함께 본다.
- 답변 내용의 사실성은 평가하지 않는다. KB 답변은 합성 데이터다.
- LLM 라우터 프롬프트는 한국어로 고정돼 있다. 영어 질의 성능은 그 조건에서의 값이다.
- LLM 라우터는 현재 질의만으로 어휘 후보(최대 20개)를 고른다(`AGENTS.md` Known gaps). 문맥 의존 케이스에서 불리할 수 있고,
  이 데이터셋의 multi-turn 케이스가 그 차이를 드러내도록 설계됐다.
- 병렬 실행 중 지연은 서로 영향을 준다. 지연 비교는 같은 `--concurrency`끼리만 한다.
