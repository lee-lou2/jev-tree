# 평가 계획

무엇을 알고 싶은지, 어떤 순서로 돌리는지, 무엇을 합격으로 보는지, 결과를 어떻게 남기는지 정한다.
지표 정의는 [METHOD.md](METHOD.md), 데이터 형식은 [DATASET.md](DATASET.md).

## 1. 목적

jev-tree가 "사람 대신 트리를 따라 내려가 지식을 찾고 저장한다"는 약속을 얼마나 지키는지 숫자로 남긴다.

1. 질문에 맞는 카테고리로 가는가 (라우팅)
2. 그 안에서 맞는 답을 맨 위에 올리는가 (랭킹)
3. 모르는 것은 모른다고 하는가 (보류·트리 밖 판정)
4. 새 지식을 맞는 곳에 안전하게 저장하는가 (ingest)
5. 위 네 가지가 라우터 설정, 트리 깊이, 후보 수, 진입점, 대화 문맥에 따라 어떻게 달라지는가

## 2. 평가 질문과 가설

| # | 질문 | 가설 | 보는 곳 |
|---|---|---|---|
| H1 | Jev만 쓸 때와 LLM 라우팅을 더할 때 무엇이 다른가 | LLM은 단일 턴 의역·키워드에 강하고 호출 수가 적다. 여러 턴 문맥, 넓은 트리(후보 20개 제한)에서는 불리할 수 있다 | `jev` vs `jev_llm` 셀 비교, ctx·style·variant 분석, Jev/LLM 호출 수 |
| H2 | 트리 깊이가 정확도·비용에 어떤 영향을 주나 | Jev 빔은 깊을수록 라운드와 오류 누적이 늘고, 얕고 넓을수록 한 단계 선택지가 많아 헷갈린다 | variant별 E2E·라우팅, 깊이별 경로 일치율, Jev 호출 수 |
| H3 | 카테고리 아이템이 아주 많거나 아주 적으면 랭킹·보류가 버티나 | 후보가 32개를 넘어 배치가 나뉘면 top1 정확도와 지연이 나빠진다. 후보가 1개뿐이면 그 아이템이 답이 아닐 때 보류해야 하는데 억지로 답할 수 있다 | pool 구간별 Hit@1(라우팅이 맞았을 때), 대용량 리프·큰 서브트리 케이스, `sparse` 셀의 dropped 케이스 E2E·오답변율, 지연 |
| H4 | 하위 카테고리(가상 루트·시작 노드)에서 검색·저장이 맞게 동작하나 | 가상 루트는 범위를 좁혀 정확도를 올리고, 범위 밖 요청은 null로 거절한다. 시작 노드는 거절할 수 없어 랭킹 보류에 기댄다 | entry별 분석, 같은 group의 forest/root 짝 비교, 루트 밖 케이스 |
| H5 | 여러 턴 문맥을 제대로 쓰나 | 지시어·생략·정정·조건 분산(slot)에서 단일 턴보다 떨어진다 | turns·ctx별 E2E |
| H6 | 보류 임계값 0.30이 적절한가 | 오답변율과 오보류율 사이의 균형점이 다를 수 있다 | 임계값 스윕 표, 오답변율·오보류율 |
| H7 | 저장이 검색만큼 정확하고 불변식을 지키나 | 초안 비노출·게시 성공은 100%. 저장 카테고리는 같은 내용의 검색 라우팅과 비슷하다. 게시 때 descent를 다시 돌아 카테고리가 바뀔 수 있다 | ingest 표, 카테고리 유지율, 기존 답변 강등 건수 |
| H8 | 표현이 흔들려도 견고한가 | 오타·영어·혼용·프롬프트 주입에서 성능 하락이 작아야 한다 | style별 분석 |

## 3. 평가 매트릭스

| 축 | 수준 | 기본 |
|---|---|---|
| 라우터 | `jev`, `jev_llm` | 둘 다 |
| 트리 변형 | `deep`(7) · `standard`(4) · `shallow`(2) · `flat`(1) · `sparse`(4, 리프당 1개) | 전부 |
| 스위트 | search · ingest · contract | 전부 |
| 진입점 | forest · 가상 루트(`root_node`) · 시작 노드(`start_node`) | 케이스에 포함 |
| 문맥 | 단일 턴 · 여러 턴(9개 패턴) | 케이스에 포함 |
| 후보 수 | 빈 리프 · 1개(`sparse`) · 2–5개 · 대용량(55–83개) · 큰 서브트리(100–230개) | 케이스와 변형에 포함 |
| 절제 실험 | beam_width 1/3/5, LLM 모델 교체, 초안 검색 검증 | 4단계에서 |

진입점·문맥·후보 수·질의 스타일은 케이스 태그로 들어 있으므로 셀 하나만 돌려도 세부 분석 표로 나온다.

## 4. 실행 단계

명령은 모두 저장소 루트에서 실행한다. 키 설정은 [README.md](README.md#키-설정).

### 0단계 — 데이터 점검 (비용 0)

```bash
cargo run --release --example eval -- validate --strict
cargo run --release --example eval -- stats --out eval/golden/STATS.md
cargo run --release --example eval -- run --mock oracle --router both --variant all
```

통과 기준: 검증 오류·경고 0, oracle 실행에서 모든 셀 라우팅 100%·저장 100%·계약 100%.

### 1단계 — 스모크 (소량)

```bash
cargo run --release --example eval -- run --router jev --sample 60 --note "smoke"
cargo run --release --example eval -- run --router jev_llm --sample 60 --note "smoke"
```

확인: 실행 오류 0, p95 지연, **Jev 호출/건**. 이 값으로 전체 실행 비용을 추정한다(6절).

### 2단계 — 기준선

```bash
cargo run --release --example eval -- run --router both --variant all --note "baseline v1.0.0"
```

10개 셀 전체(2 라우터 × 5 변형). 이 실행을 기준선으로 [results/README.md](results/README.md)의 기준선 표에 적는다.

### 3단계 — 안정성

```bash
cargo run --release --example eval -- run --router both --sample 120 --repeat 3 --note "stability"
```

같은 착지·같은 top1 비율이 잡음 바닥이다. 이후 비교에서 이보다 작은 차이는 변화로 보지 않는다.

### 4단계 — 절제 실험

| 실험 | 명령 | 보는 것 |
|---|---|---|
| 빔 폭 | `run --beam-width 1` / `--beam-width 5` | 정확도 대비 호출 수 |
| LLM 모델 | `JEV_EVAL_LLM_MODEL=<다른 모델> run --router jev_llm` | 모델별 라우팅 차이 |
| 초안 검색 검증 | `run --suite ingest --verify-draft-search` | 초안이 실제 검색에도 안 나오는지 |
| 후보 수 | `run --variant standard,sparse` | 같은 질문에서 후보가 많을 때와 1개일 때 |
| 보류 임계값 | 기준선 리포트의 스윕 표 | 0.30 조정 필요성 (코드 변경 없이) |

### 5단계 — 회귀 운용

`src/engine.rs`, `src/jev.rs`, 분류 트리 설명을 바꾸는 변경마다:

```bash
cargo run --release --example eval -- run --router both --split test --note "PR #N"
cargo run --release --example eval -- compare eval/results/runs/<기준선> eval/results/runs/<이번 실행>
```

## 5. 합격 기준

### 5.1 항상 지켜야 하는 것 (게이트)

| 항목 | 기준 |
|---|---|
| API 계약 통과 | 100% |
| 초안 비노출 | 100% (불변식 6) |
| 게시 성공 | 100% |
| 실행 오류율 | 1% 이하 (Jev·LLM 장애 제외 후 재실행) |
| oracle mock | 모든 셀 라우팅·저장·계약 100% |

### 5.2 회귀 판정 (기준선 대비, 같은 데이터셋 버전)

- `test` split의 E2E 정답률·라우팅 정확도·Hit@1이 **McNemar p < 0.05로 유의하게 떨어지면 불합격**.
- 오답변율이 유의하게 오르면 불합격 (틀린 답을 자신 있게 내는 것이 가장 비싸다).
- 유의하지 않은 차이는 3단계 잡음 바닥과 함께 기록만 한다.

### 5.3 절대 목표 (기준선 측정 후 확정)

2026-09-23 기준선(`20260923-183745-jev`, `jev` 라우터, `jev-latest`)에서 확정했다.
기준선을 넘으면 합격으로 보고, 기준선에서 떨어진 항목을 개선 과제로 둔다.

| 지표 | `deep` | `standard` | `flat` | 목표 (standard) |
|---|---:|---:|---:|---:|
| E2E 정답률 | 91.5% | 91.7% | 97.2% | **>= 91.7%** |
| 라우팅 정확도 | 88.7% | 90.0% | 97.5% | **>= 90.0%** |
| Hit@1 | 90.5% | 91.3% | 97.2% | **>= 91.3%** |
| 트리 밖 판정 F1 | 0.764 | 0.764 | 1.000 | **>= 0.764** |
| 오답변율 | 3.1% | 4.7% | 0.0% | **<= 4.7%** |
| 막연한 질문(internal) E2E | - | 67.6% | - | **>= 67.6%** (개선 과제) |
| 저장 정확도 | 86.8% | 88.2% | 100.0% | **>= 88.2%** (개선 과제) |
| p95 지연 | 6.0s | 6.5s | 1.7s | **<= 6.5s** |
| 실행 오류율 | 0% | 0% | 0% | **0%** |

`jev_llm` 쪽 목표는 그 라우터의 기준선이 생긴 뒤 같은 형식으로 채운다.

**개선 과제** (기준선에서 목표를 못 넘은 항목)

1. **막연한 질문의 내부 노드 멈춤** — `vague` 스타일 E2E 56.5%, 내부 노드 착지 67.6%.
   랭킹이 하위 서브트리 전체를 점수화해 내부 노드의 개요 항목을 맨 위에 올리기 어렵다.
2. **범위 밖 Q&A 거절** — ingest 거절 66.7%(4/12). 라우팅이 트리 안으로 끌어오면 거절할 수단이 없다.

## 6. 비용과 시간

엔진 동작에서 호출 수를 추정할 수 있다.

| 요청 | Jev 호출 | LLM 호출 |
|---|---|---|
| search (jev) | 빔 라운드(변형 깊이 이하: flat 1, shallow 2, standard ≤ 4, deep ≤ 7) + ⌈후보 수 / 32⌉ | 0 |
| search (jev_llm) | ⌈후보 수 / 32⌉ | 1–2 (+ 형식 재시도) |
| ingest 시나리오 | 초안 descent + 게시 descent (+ probe 검색) | jev_llm이면 descent마다 1–2 |

후보 수는 보통 리프 2–5개(배치 1회), 대용량 리프 50–90개(2–3회), 영역 루트에 멈추면 수백 개(10회 이상)다.
실제 값은 스모크 리포트의 "Jev 호출 수 평균"을 쓴다.
참고 실측(데이터셋 구축 직후 하네스 점검 5건, jev/standard): search 1건 1.2–1.7초, ingest 시나리오(초안+게시+probe) 3.0초.
이 속도면 셀 하나(약 500건)는 concurrency 4에서 수 분 안쪽이다. 5건으로 잰 값이라 대략적이다.

**전체 추정** = Σ(셀별 케이스 수 × 호출/건). `run --dry-run`이 셀별 케이스 수를 먼저 보여 준다.
시간은 대략 `케이스 수 × 건당 지연 ÷ concurrency`다. 병렬도를 올리면 속도는 빨라지지만 제공자 한도(429)에 걸릴 수 있다.
Jev 클라이언트는 408·429·5xx에 두 번까지 재시도한다.

## 7. 결과 기록

- 실행마다 `eval/results/runs/<run_id>/`에 `meta.json`(설정·git·데이터셋 해시), `cells/*.jsonl`(케이스별 원시 결과와 판정),
  `summary.json`, `report.md`가 생긴다. 키·토큰은 남지 않는다.
- 실행마다 `eval/results/history.csv`에 셀당 한 줄이 추가된다. 시계열 비교는 이 파일로 한다.
- 기준선, 중요한 비교, 해석은 [results/README.md](results/README.md)의 기록표에 적는다.
- mock 실행은 임시 폴더에 남고 history에 쓰지 않는다.

## 8. 데이터셋 운영

- **dev/test**: 케이스의 약 30%가 id 해시로 `test`에 들어간다. 트리 설명·프롬프트를 고칠 때는 dev의 실패만 보고,
  효과는 test로 확인한다. test 실패를 보고 설명을 고치면 test가 오염된다.
- **라벨 수정**: 모델 출력에 맞춰 라벨을 바꾸지 않는다. 라벨이 틀렸다는 근거(노드 설명과의 불일치)를 `note`에 적고 두 사람이 본다.
- **케이스 추가**: 운영에서 나온 실패 사례는 개인정보를 지우고 의역해서 추가한다. 추가하면 minor 버전을 올린다.
- **노드 변경**: 트리 구조가 바뀌면 major 버전을 올리고 기준선을 다시 잡는다.
- 변경 후에는 항상 `validate --strict`와 oracle mock을 통과시킨다.
