# eval/large — 대규모 합성 벤치마크

> **In English** — A synthetic Korean benchmark ten times the size of the golden set:
> 1,902 nodes, 14,870 items, 3,860 cases. The golden set's tree fits in one Jev choice
> (254 options), so it cannot show what happens when a tree does not; this one does.
> Same schema and runner as `eval/`: pass `--eval-dir eval/large`.

기존 골든셋(`eval/`, 219노드·669아이템)은 트리 전체가 Jev 선택지 한 번(254개)에 들어간다.
그래서 "트리가 한 번에 안 들어갈 때"를 재지 못한다. 이 벤치마크는 그 상황을 만든다.

## 한눈에

| | |
|---|---|
| **지식베이스** | 33개 영역, 노드 1,902개(리프 1,420 · 중간 482), 최대 깊이 4, 아이템 14,870개 |
| **리프당 아이템** | 4–6개 20% · 8–12개 70% · 20개 7% · 40개 3% (같은 리프 안의 비슷한 아이템이 랭킹을 시험) |
| **중간 노드** | 노드마다 개요 article 1개 (막연한 질문이 거기 멈췄을 때의 답) |
| **케이스 3,860** | 검색 3,700 = 답 있음 2,964 · 답 빠짐 107 · 막연한 질문 449 · 범위 밖 180 / 저장 160 |
| **질의 스타일** | 바꿔 말하기 22% · 구어체 16% · 긴 상황 설명 13% · 여러 턴 13% · 키워드 9% · 조건 8% · 오타·영어·혼용 각 5% · 부정 4% |
| **변형** | `full`(원본) · `standard`(fine 단계 제거) |

영역 경계는 일부러 겹치게 설계했다. 예: 개인 카드(card) ↔ 회사 법인카드(payroll) ↔ 쇼핑몰 환불(returns),
개인 계정(security) ↔ 사내 계정(itdesk) ↔ 와이파이 비밀번호(net), 해외송금(bank) ↔ 환전(abroad),
전입신고(civil) ↔ 이사(house), 실손보험(insure) ↔ 건강보험 급여(medical). 각 영역의 설명이 그 경계를 말한다.

## 실행

```bash
cargo run --release --example eval -- validate --eval-dir eval/large
cargo run --release --example eval -- run --eval-dir eval/large --variant full --router both \
    --sample 1500 --seed final --concurrency 6
```

`--sample 1500 --seed final`은 0.10.0 측정에 쓴 표본이다(같은 시드면 같은 케이스).

## 만든 방법

데이터는 모두 LLM(`meta/muse-spark-1.3-contributor`)으로 단계별로 만들고, 라벨은 별도 판정 호출로 검증했다.
생성 스크립트는 저장소에 두지 않았다(런타임에 Python이 없다는 원칙). 단계와 규칙은 다음과 같다.

1. **분류 트리** — 영역마다 한 번 호출. 영역 33개의 범위와 이웃 영역과의 경계를 함께 주고, 1단계 6–8개 ×
   2단계 4–7개(일부 3단계 2–4개)를 받는다. 형제는 상호 배타적, 설명에는 형제·이웃과의 차이를 쓰게 했다.
   이름이 겹치면 `이름(부모 이름)`으로 바꿔 전체에서 유일하게 했다.
2. **아이템** — 리프마다 호출. 경로·설명·형제 분류(넣으면 안 되는 주제)를 주고, 서로 다른 구체적 하위 질문과
   1–3문장 답을 받는다. 가상의 회사(한빛테크)·쇼핑몰(모아몰) 영역만 그 회사 규정처럼 지어내게 했다.
3. **개요와 막연한 질문** — 영역마다 호출. 중간 노드마다 하위 분류로 안내하는 article과, 하위 분류를 특정할
   조건이 없는 막연한 질문 하나.
4. **질의** — 리프마다 호출. 목표 아이템 2개(아이템 20개 이상이면 3개)에 스타일을 정해 주고, 그 아이템으로만
   답이 되고 같은 리프의 다른 아이템으로는 안 되는 질문을 받는다. 리프의 약 11%는 아이템 하나를 KB에서 빼고
   그 아이템의 질문을 "답 빠짐"(보류가 정답)으로, 약 11%는 하나를 빼서 저장 케이스로 썼다.
5. **범위 밖** — 주제 12묶음(먼 주제 6, 가까워 보이는 주제 6)으로 생성한 뒤, 영역·1·2단계 전체를 본 판정기가
   "다루지 않는다"고 한 것만 남겼다(192개 중 180개).
6. **라벨 검증** — 질의마다 판정 호출. 같은 리프의 아이템(질문+답)과 형제 리프의 질문을 보여 주고 "바로 답이
   되는 항목"을 고르게 했다. 목표 아이템을 고르지 않으면 버리고(2,970개 중 6개, 0.2%), 답 빠짐 질의에 남은 아이템을
   고르면 버렸다(133개 중 26개, 19.5%). 다른 아이템을 고르면 그것도 정답(등급 2)으로 넣는다.

## 한계 — 숫자를 읽기 전에

- **합성 데이터다.** 답변의 사실성은 평가 대상이 아니다. 라우팅·랭킹·보류만 본다.
- **엄격 라벨은 정확도를 낮게 잡는다.** 영역 경계를 일부러 겹치게 만든 데다 LLM이 만든 트리라 형제끼리도
  범위가 일부 겹친다. 오류로 잡힌 케이스를 보면 "결로"를 수면 환경이 아니라 창틀 결로 분류로 보내는 식으로,
  시스템 답이 더 그럴듯한 경우가 적지 않다. 절대값보다 **같은 케이스로 짝지은 비교**(`compare`)를 본다.
- 질의를 만든 모델과 LLM 리뷰에 쓰는 모델이 같다. 생성 단계에서 아이템 문구를 베끼지 말라고 지시했지만,
  LLM 리뷰의 이득은 조금 과대평가됐을 수 있다. Jev만 쓰는 수치에는 해당하지 않는다.
- 판정기는 같은 리프와 형제 리프만 본다. 먼 영역의 동등한 아이템은 정답으로 잡히지 않는다.
- 0.10.0 측정 뒤 커밋하기 전에, 생성기가 지어낸 전화번호 모양 문자열 5개(질의 2·아이템 3)를
  `eval/tools/secret-scan.sh`가 통과하도록 `010-XXXX-XXXX`처럼 가렸다. 그래서 `eval/results/runs/20261021-large-*`의
  `kb_hash`·`cases_hash`는 지금 파일과 다르다. 케이스 id는 같아서 `compare`는 그대로 짝지어진다.
